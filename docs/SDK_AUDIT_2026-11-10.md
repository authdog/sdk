# Authdog SDK Audit Report

**Date**: 2026-11-10  
**Auditor**: Automated SDK Audit  
**Repository**: `authdog/sdk`  
**Scope**: All 7 core SDKs (Node.js, Python, Go, Rust, Java, C#, Zig)

---

## Executive Summary

The Authdog SDK monorepo provides official client libraries across 7 languages, wrapping 277 platform API operations (Waves 1-5). The codebase demonstrates solid architectural foundations with consistent cross-language structure, comprehensive type definitions, and well-organized CI pipelines. However, significant gaps exist in framework integrations, developer experience tooling, test coverage infrastructure, release automation, and platform/CLI alignment that limit adoption and maintainability.

**Overall Maturity**: Early Production (suitable for API consumption, but missing ecosystem integrations expected by developers familiar with Clerk/WorkOS SDKs)

## 2. Top Findings with Evidence

### Finding 1: Missing Framework Integrations (HIGH IMPACT)

**Issue**: All SDKs are low-level HTTP clients with no middleware or framework adapters.

**Evidence**:
- `node/src/` contains only `client.ts`, `types.ts`, `resources.ts`, `exceptions.ts` — no Express/Fastify/NestJS middleware
- `python/authdog/` has no FastAPI/Django/Flask integration modules
- `go/` has no Gin/Echo/Fiber middleware
- `java/` has no Spring Boot starter or auto-configuration
- `csharp/` has no ASP.NET Core `AddAuthdog()` extension

**Comparison with Competitors**:
- **Clerk**: Ships `@clerk/nextjs`, `@clerk/express`, `@clerk/fastify`, `@clerk/remix` as first-class packages
- **WorkOS**: Provides `@workos-inc/express` middleware, `@workos-inc/nextjs` integration

**Impact**: Developers must manually wire authentication middleware, session handling, and route protection.

### Finding 2: No Typed Request/Response Bodies for Management Operations (MEDIUM IMPACT)

**Issue**: Management resource methods use generic `Json` / `dict` / `any` types for request bodies and many responses.

**Evidence** (`node/src/resources.ts`):
```typescript
// Line 67-69
create(body: Json): Promise<Json> {
  return this.client.request('POST', '/v1/organizations', { data: body });
}
```

**Evidence** (`python/authdog/resources.py`): Methods accept `Dict[str, Any]` bodies.

**Impact**: No compile-time/lint-time validation of API payloads. Developers discover errors at runtime.

### Finding 3: Test Coverage Infrastructure Gaps (MEDIUM IMPACT)

**Issue**: No coverage thresholds enforced, no coverage badges, no integration tests.

**Evidence**:
- `node/vitest.config.ts` configures coverage but no threshold:
  ```typescript
  coverage: {
    provider: 'v8',
    reporter: ['text', 'lcov', 'html'],
    // No 'lines', 'branches', 'functions' thresholds
  }
  ```
- No `coverage.xml` committed or referenced in CI
- GitHub Actions upload artifacts but don't fail on coverage drops

**All test files** use mocked HTTP clients — no integration tests against a staging/sandbox API.

### Finding 4: Incomplete Error Context (MEDIUM IMPACT)

**Issue**: API errors don't include request ID, response body, or retry guidance.

**Evidence** (`node/src/exceptions.ts`):
```typescript
export class APIError extends AuthdogError {
  statusCode?: number;
  constructor(message: string, statusCode?: number) {
    super(message);
    this.name = 'APIError';
    this.statusCode = statusCode;
  }
}
```

Missing: `requestId`, `responseBody`, `retryAfter`, `rateLimitRemaining`.

**Comparison**: Stripe SDK includes `request_id`, `charge`, `decline_code` in error objects.

### Finding 5: No Release Automation or Changelog (HIGH IMPACT)

**Issue**: No automated release pipeline, no CHANGELOG.md files, no release-please/semantic-release integration.

**Evidence**:
- No `.github/workflows/*-release.yml` files
- No `CHANGELOG.md` in root or SDK directories
- No `release.config.js` or `.release-please-manifest.json`
- Manual version strings in `package.json`, `pyproject.toml`, `Cargo.toml`, etc.

**Impact**: Releases require manual coordination. Version history is undocumented.

### Finding 6: Missing Dependency Security Scanning (MEDIUM IMPACT)

**Issue**: No Dependabot/Renovate configuration. Only Java has OWASP scanning.

**Evidence**:
- No `.github/dependabot.yml`
- No `renovate.json`
- `java/pom.xml` includes OWASP dependency-check plugin
- `rust/Cargo.toml` has no `cargo audit` in CI

**Evidence** (`java/pom.xml` line 48):
```xml
<owasp.version>8.4.0</owasp.version>
```

No other SDK has equivalent security scanning.

### Finding 7: CLI/SDK Alignment Gaps (MEDIUM IMPACT)

**Issue**: The SDKs don't integrate with CLI workflows or share configuration patterns.

**Evidence**:
- CLI has `authdog init` that writes `.authdog/project.json` — SDKs don't read this
- CLI has `authdog mcp install` — no SDK equivalent for MCP registration
- CLI has `authdog config pull` — SDKs don't support config file loading
- No shared environment variable conventions documented

**CLI README** documents these commands:
```
authdog init
authdog config pull
authdog mcp install --client cursor
```

SDKs don't consume or produce compatible artifacts.

### Finding 8: Documentation Gaps (MEDIUM IMPACT)

**Issue**: Missing migration guides, debugging guides, and interactive examples.

**Evidence**:
- No `docs/` folder (this report creates it)
- No `MIGRATION.md` for version upgrades
- No `TROUBLESHOOTING.md`
- No runnable examples beyond README snippets
- No API reference beyond README method lists

**Comparison**: Clerk has https://clerk.com/docs with guides, tutorials, API reference, and changelog.

### Finding 9: Inconsistent Pagination/Filtering Patterns (LOW IMPACT)

**Issue**: List operations have inconsistent parameter patterns across SDKs.

**Evidence** (`node/src/resources.ts` line 333-350):
```typescript
list(
  tenantId: string,
  environmentId: string,
  query?: { offset?: number; limit?: number; searchQuery?: string }
): Promise<EnvUsersResponse>
```

vs `go/resources.go` uses positional parameters.

**Impact**: Developers must learn different patterns when switching SDKs.

### Finding 10: No Retry/Backoff Logic (LOW IMPACT)

**Issue**: SDKs don't implement retry logic for transient failures or rate limits.

**Evidence**: No retry loop in any `client.*` file. All HTTP calls are single-attempt.

**Comparison**: AWS SDKs, Stripe SDK implement exponential backoff by default.

## 5. Open Questions

### Architecture Questions

1. **Should framework integrations live in this monorepo or separate repos?**
   - Pro monorepo: Atomic releases, shared CI
   - Pro separate: Independent versioning, smaller packages
   - Recommendation: Start in monorepo under `node-express/`, `python-fastapi/`, etc.

2. **Should we generate SDK code from OpenAPI spec?**
   - The platform has an OpenAPI spec (`specs/004-api-parity/contracts/openapi.snapshot.json`)
   - Generation would ensure API parity but may lose hand-tuned ergonomics
   - Recommendation: Generate types only, keep hand-written client logic

3. **What is the testing strategy for planned SDKs promotion?**
   - Current: Manual promotion from `planned/` to root when ready
   - Missing: Promotion checklist, minimum requirements
   - Recommendation: Define explicit promotion criteria in CONTRIBUTING.md

### Platform Questions

4. **Is there a staging/sandbox Authdog API for integration tests?**
   - Current tests mock all HTTP calls
   - Integration tests need a non-production endpoint
   - Action: Confirm with platform team

5. **What is the versioning strategy for API waves?**
   - SDKs currently ship all waves together at 0.2.0
   - Should new waves be behind feature flags?
   - Should old waves be deprecated/removed in future majors?

6. **How should SDK versions relate to CLI versions?**
   - CLI is at different release cadence
   - Should there be compatibility matrix documentation?

### Process Questions

7. **Who reviews SDK PRs across languages?**
   - Risk: Changes in one SDK not reflected in others
   - Recommendation: CODEOWNERS with cross-SDK reviewers

8. **Is there a design review process for new features?**
   - Current: Spec-kit specs, but unclear review flow
   - Recommendation: RFC process for cross-cutting changes
